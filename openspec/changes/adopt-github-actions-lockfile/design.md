## Context

### The GitHub format

Source of truth: [`github/actions-lockfile`](https://github.com/github/actions-lockfile) (Go parser + JSON Schema) and its producer [`github/gh-actions-lock`](https://github.com/github/gh-actions-lock). Read at `actions-lockfile@ac15883` (2026-10-09). Both are pre-1.0 and say the schema may change.

- **Path**: `.github/workflows/actions.lock` (`lockfile.Path` in [`lockfile.go`](https://github.com/github/actions-lockfile/blob/main/go/pkg/lockfile/lockfile.go)).
- **Schema** [`v0.0.3`](https://github.com/github/actions-lockfile/blob/main/schema/lockfile-v0.0.3.json): top-level `version` (const `v0.0.3`), `workflows`, `dependencies`. `additionalProperties: false` at every level, so gx cannot add its own fields.
- **Pin key**: `OWNER/REPO@REF`. Owner and repo are lowercased; the ref keeps its case. Sub-action paths are dropped (`actions/cache/save@v4` → `actions/cache@v4`): the runner downloads a repo+ref once.
- **Dependency entry**: `ref` (required; for a SHA key it is the discovered tag/branch, priority *full semver tag > any tag > branch*), `commit` (required, `sha1-<hex>`), `owner_id`, `repo_id` (required, positive), `uses` (direct child pins, composite actions only), `hostname` (omitted on github.com).
- **Parser checks**: body `ref` must equal the key's ref unless the key ref is a full SHA; for a SHA key, `commit` must equal it; `uses` graph must be acyclic; workflow keys must be safe repo-relative paths.
- **Writer conventions** (`marshalDeterministic` in [`state_marshal.go`](https://github.com/github/gh-actions-lock/blob/main/internal/lockfile/state_marshal.go)): a three-line header comment; workflows, their pin lists, dependency keys and `uses` lists all sorted; every user-supplied scalar single-quoted; schema keys plain; 4-space indent (yaml.v3 default); empty `workflows`/`dependencies` omitted.
- **Onboarding**: a workflow is enforced when its path is a key in `workflows`. Workflows using `./` local actions [cannot be onboarded yet](https://github.com/github/gh-actions-lock#limitations); the CLI skips them or migrates `./` to the new `$/` same-repo syntax.
- **Not covered by the lock**: `docker://` images, `./` and `$/` references, remote reusable workflows (`owner/repo/.github/workflows/x.yml@ref`: `ParseActionRef` rejects them and the CLI does not record them).
- **Availability**: public preview for GitHub Enterprise Cloud, with an admin "Require lockfile" policy ([daily.dev summary of the changelog](https://daily.dev/posts/github-actions-workflow-lockfiles-in-public-preview-3zoik06ky), [GitHub Docs](https://docs.github.com/en/actions/how-tos/secure-your-work/lock-workflow-dependencies)). The changelog post itself was not reachable from the environment this design was written in.

### How gx's lock differs today

| | `.github/gx.lock` | `.github/workflows/actions.lock` |
|---|---|---|
| Read by | gx only | the runner, `gh actions-lock`, any parser user |
| Key | (action ID incl. subpath, version) | `owner/repo@ref`, subpath dropped |
| Specifier → version | `[resolutions]` tier | not stored |
| Commit | `sha` | `commit: sha1-…` |
| Ref kind | `ref_type` (tag/release/branch/commit) | not stored; only the `ref` string |
| Commit date | `date` | not stored |
| Repository identity | name only | name + `owner_id` + `repo_id` |
| Per-workflow membership | no (overrides live in the manifest) | `workflows:` map |
| Transitive (remote composite) deps | no | yes, via `uses:` |

## Goals / Non-Goals

**Goals**

- The lockfile gx writes is the file GitHub enforces, at the path GitHub reads, and is accepted by `lockfile.Parse`.
- gx and `gh actions-lock` produce byte-identical files for the same pins, so a repo can use both (e.g. gx to upgrade, `gh actions-lock --verify` in CI) without diff noise.
- No security regression for repositories without runner enforcement: workflows stay SHA-pinned.
- No user is left with a broken workflow: gx never onboards a workflow the runner would reject.
- One-step, lossless migration from `gx.lock`.

**Non-Goals**

- GHE.com data residency and GHES. gx is github.com-only (`Forge::GitHub`); `hostname` is never written. A lockfile carrying a `hostname` is read, and written back unchanged.
- Rewriting `./` local actions to `$/`. That syntax is part of the same preview; adopting it is a separate decision.
- Locking `docker://` images or remote reusable workflows: the format does not cover them.
- Re-implementing `gh actions-lock --verify` (reachability and impostor-commit checks). The runner and the CLI own that; gx records correct data.
- Supporting both lockfiles side by side long term.

## Decisions

### Decision 1: Replace `gx.lock`, don't write both

Two lockfiles describing the same pins drift, and users must learn which one wins. Every fact gx reads from `gx.lock` is either in `actions.lock` or derivable (Decision 4). Keeping `gx.lock` would only preserve `date`, which nothing reads.

**Rejected — emit `actions.lock` as an export next to `gx.lock`:** doubles the review surface and the hook work, and the export would be the only file anyone else trusts.

### Decision 2: Keep SHA pins in workflows; key them by SHA in the lockfile

`gx tidy` keeps writing `uses: actions/checkout@de0f…83dd # v6.0.2`. The pin key is `actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd`, `ref: 'v6.0.2'`, `commit: 'sha1-de0f…83dd'`. This is the shape `gh actions-lock` itself writes for a SHA `uses:` (see `actions/attest-build-provenance@36fa…` above) and the parser explicitly allows it (`rejectKeyRefMismatch` skips full-SHA keys).

- Repos without the preview keep today's guarantee.
- Repos with it gain repository-identity and onboarding enforcement on top.
- `ref` is the version gx already resolves and writes in the comment, so the two never disagree.

**Rejected for now — write tag refs (`@v6.0.2`) and rely on the lock:** that is the idiomatic GitHub flow, but it silently drops immutability wherever the runner does not enforce the lock (every non-GHEC repo during the preview). It can come later as an opt-in manifest setting once enforcement is generally available.

### Decision 3: Byte-compatible writer, hand-built

The writer reproduces `marshalDeterministic`: same header text (naming gx, see below), same sort order, same quoting, 4-space indent, empty sections omitted. The output shape is fixed and small, so it is emitted with a small line builder that quotes every scalar through one function (single quotes, `'` doubled), rather than through a YAML serializer whose styling gx would have to fight. The existing guardrail ("TOML generation uses a document builder, not string formatting") is restated for YAML: the builder owns quoting; no call site formats a scalar.

The header names the producer: `# This file is machine-generated by \`gx\`.` / `# Do not edit by hand; run \`gx tidy\` to update.` / `# Docs: https://gh.io/actions-lockfile`. Comments are not part of the schema, so this is the one intentional difference from the CLI's bytes. When gx rewrites a file whose header names another producer, it keeps the existing header, so alternating tools never flip it.

Pins are lowercased exactly as `Pin.Canonical` does (owner and repo only).

### Decision 4: Derive the resolution tier and ref kind

- **Specifier → version**: for manifest entry `actions/checkout = "^6"`, the resolved version is the `ref` of the pin the workflow uses. With per-workflow membership this is more precise than today: an override workflow's pin is found through its own `workflows:` list, not a global `(action, specifier)` key.
- **Completeness**: a pin is complete when it has `ref`, `commit`, `owner_id` and `repo_id`, plus `uses` when the action is composite (Decision 5). Missing IDs trigger only the ID lookup, as missing metadata triggers targeted repair today.
- **Ref kind** (`mutable-ref` audit check, upgrade): a `ref` that parses as a version is a tag; any other ref is looked up when needed (`audit` already requires a token). The CLI's priority rule means a branch is recorded only when no tag points at the commit, so a non-version `ref` is a branch candidate, not proof.
- **`date`**: dropped. Nothing reads it.

### Decision 5: Resolve remote composite actions transitively

For each locked repository action gx reads `action.yml` (then `action.yaml`) at the locked commit, from the action's subpath. If `runs.using` is `composite`, each step `uses:` is classified exactly like a workflow `uses:` and resolved at the ref it names, *without* rewriting the remote file and *without* consulting the manifest (the user does not own that ref). The child pin keys go in the parent's `uses:`; the workflow's list gets the full closure. Cycles are a resolution error naming the cycle (the parser rejects them anyway).

Child pins keep the ref the composite wrote (`actions/setup-go@v5`, not narrowed), matching the CLI, so both tools agree on keys.

### Decision 6: Which workflows go in `workflows:`

A file under `.github/workflows/` is listed iff it contains at least one lockable `uses:` and no step-level `./` action reference. Local composite actions under `.github/actions/` are never keys. A workflow reaches them through `./`, so that workflow is excluded by the rule above; their remote dependencies become part of a workflow's closure only once `$/` is adopted (Open Question 3). A workflow with no `uses:` at all is listed with an empty list, matching the CLI's "onboarded with no dependencies".

A skipped workflow produces one warning: `"<path>" uses local action "./…"; GitHub cannot enforce the lockfile for it yet, so it was left out of actions.lock`.

Remote composite actions referenced only from `.github/actions/` still need their pins in `dependencies` (otherwise `gx tidy` would drop them, regressing the "action referenced only by a composite action is retained" requirement). They are kept as unreferenced-by-workflow dependencies. The parser accepts them; the CLI's full run would prune them, which is the one known case where the two tools disagree. Listed under Open Questions.

### Decision 7: Migration

On load, if `actions.lock` is absent and `.github/gx.lock` exists, gx reads `gx.lock` through the existing readers, maps each action entry to a SHA-keyed pin (`ref` = the gx version), fetches IDs and composite children, writes `actions.lock`, and deletes `gx.lock`. Versions are not re-resolved, so migration never changes what runs. If both files exist, `actions.lock` wins and gx warns that `gx.lock` is stale and can be deleted.

### Decision 8: Read leniently, write strictly

The reader accepts v0.0.1–v0.0.3 like `lockfile.Parse`, rejects a newer version with "written by a newer tool" (never overwrites it), and fails loudly on a corrupt file instead of treating it as empty (the CLI's `ErrCorruptLockfile` rule: silently starting fresh would discard pins). The writer always writes `v0.0.3`. This replaces the current spec's "forward-compatible reads ignore unknown keys" for the lock: the schema is closed, and a key gx does not know may be a security field.

## Risks / Trade-offs

- **Preview format churn.** Schema bumped three times before preview. Mitigation: one module owns read/write; a golden test pins bytes against a file produced by `gh actions-lock`; version check fails closed.
- **More API calls.** One repo lookup per repository and one file read per locked action, both cached. For gx's own repo: 8 repos → ~16 extra requests on first lock, ~0 after (IDs and children are already in the file; only new pins resolve).
- **Unauthenticated limit (60/h).** Transitive resolution can multiply requests on a cold lock. Existing retry/skip handling applies; a pin with a failed child lookup is written without `uses` and reported incomplete, so the next run repairs it.
- **Breaking file move.** One-time diff for every user. Mitigated by automatic migration and a changelog entry.

## Automated Test Strategy

- **Unit (format)**: round-trip of a fixture copied from `gh-actions-lock`'s own lockfile is byte-identical; header preserved; quoting of YAML-ambiguous refs (`'1.0'`, `'on'`, refs containing `'`); sort order; empty sections omitted; future version and corrupt file are errors; v0.0.2 input written back as v0.0.3.
- **Unit (domain)**: pin canonicalization and subpath collapse; workflow inclusion rule (`./` excluded, `./…/workflow.yml` reusable ignored, `docker://` ignored); closure flattening; cycle detection; derived specifier → version.
- **Integration** (`tests/`, fake registry): `gx tidy` on a fresh repo writes `actions.lock` and SHA pins; a composite remote action adds children; migration from a `gx.lock` fixture produces the expected file and deletes the old one without calling `lookup_sha`; both files present → warning, `gx.lock` untouched.
- **Conformance (opt-in, not in required CI)**: a script that runs the upstream Go parser over gx output (`go run` against `actions-lockfile`), to catch schema drift. Not required CI because it needs Go and network.
- Critical path: the format round-trip and the migration test. New infrastructure: fake `repo_ids` and `action_file` methods on the test registry.

## Observability

- Migration prints one line naming both paths. Skipped workflows warn once each. A stale `gx.lock` alongside `actions.lock` warns on every run until deleted.
- Corrupt or future-version lockfile: hard error naming the file and line (from the YAML parser), never a silent rewrite.
- A failed ID or `action.yml` lookup follows existing error classification: rate-limit/auth → warning and the pin is left incomplete (repaired next run); not-found → error, since the runner would reject that pin.
- No failure path writes a lockfile that drops pins it read.

## Open Questions

1. **Composite-only pins**: keep them in `dependencies` (gx semantics, CLI would prune) or drop them (CLI semantics, gx loses track)? Proposed: keep, revisit when `$/` is adopted, which makes them reachable from a workflow.
2. **Tag-ref mode**: when enforcement is generally available, should gx offer `uses: owner/repo@vX.Y.Z` + lock as an opt-in instead of SHA pins?
3. **`$/` migration**: should `gx tidy` rewrite `./` to `$/` so those workflows can be onboarded? Depends on runner support outside the preview.
